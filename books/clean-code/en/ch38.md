# Afterword

“When you’re a carpenter making a beautiful chest of drawers, you’re not going to use a piece of plywood on the back, even though it faces the wall and nobody will ever see it. You’ll know it’s there, so you’re going to use a beautiful piece of wood on the back. For you to sleep well at night, the aesthetic, the quality, has to be carried all the way through.”

—Steve Jobs

Aspiring to avoid a colleague quoting The Hitchhiker’s Guide to the Galaxy ’s “...probably the oddest thing in the universe” when talking about your code is likely a noble pursuit. This was, of course, in reference to the legendary Babel Fish, which could translate any alien language directly into your ear.

I am often reminded of The Hitchhiker’s Guide to the Galaxy when thinking of or reading Clean Code —not just because my father loves the book series and encouraged all of his children to read it, not only because he references it in Clean Code along with his other books, and not only because Clean Code inspires deep thought. I am reminded of The Hitchhiker’s Guide to the Galaxy because Clean Code is the must-have companion guide to navigating the ever-changing universe of software development.

This is not to say that this book will automagically allow you to understand any code. On the contrary, Clean Code is the inverted Babel Fish that you place at your fingertips so that other developers don’t need a Babel Fish to understand your code!

When I was in seventh grade, my dad had me code one of my first games: Hunt the Wumpus . It is a simple text-based adventure game whereby you traverse a cave to find and terminate the wumpus while avoiding traps, pits, and whatever else a clever developer can code to challenge you.

Years later, I was volunteering at the Agile Conference in

2007. A workshop room had been set up for attendees to sit down and pair-program on a Hunt the Wumpus game built in Java. After hearing some great talks, I was eager to do some coding, so I took a sticky note off a community-managed Kanban-style whiteboard and sat down to start adding a new “fire arrow” feature. Soon after, none other than Ward Cunningham sat down beside me to start pairing. Being the young tyke that I was, I didn’t recognize I was now coding with the man who built the first wiki.

Unabashed, I charged forward and explained the feature to my new pair, and my plan to create an inheritance structure that would allow us to add not only “fire arrows” but also “ice arrows” or “arcane arrows” and so on. He nodded his head with grandiose solemnity and encouraged me to proceed.

I started by writing a test for a new Arrow class, which would later be the parent for our FireArrow class. I had already written this game, so I totally knew what I was doing. Once I had my failing test, I passed Ward the keyboard. He dutifully made the test pass, but then paused with a meaningful “hrmmpph” and proceeded to query whether we really ought to introduce such complexity so early. He posited that rather than jumping to our end-state architecture, we might try to add the functionality gradually and allow the test-driven process to reveal an appropriate shape. Frustrated because I knew how it ought to be architected, I begrudgingly agreed to follow his lead. I was here to learn, after all.

His next move shocked me. He opened up the class with the code that launched the arrows and proceeded to comment a bunch of it out! Aghast, I righteously protested, thinking we were going backward rather than forward! In response, he showed how “everything is still green,” all the tests were passing, and that we might be able to get away with a little refactoring. The next 30 minutes passed in a series of moments of awe.

First, we did a number of subtle refactorings, adding a few tests and renaming/extracting some functions. I remember being struck by the fluidity in which he moved through the phases of red, green, refactor. It became abundantly clear that this wasn’t just a process he used while coding. It was a principle to him—a way of thinking, problem-solving, and producing clean and clear results so ingrained into his workflow that the tests and the code were really one and the same.

Second, we began adding the new functionality for a “fire arrow.” Now that everything was neatly laid out, this was simple. He wrote the failing test. I made it pass in what couldn’t have been more than a line or two of code. I had finished making it pass before even realizing we had actually completed the feature. When it dawned on me, he nodded appreciatively.

Next, he prompted me to grab the next feature. I seem to recall grabbing “ice arrow” but then being instructed toward greater ambition, and grabbed “crossbow bolt” instead, as it was going to be more challenging. However, after writing the failing test and passing Ward the keyboard, I knew my assumption was wrong, and it was remarkably simple to add this totally new weaponization against the wumpus.

Finally, after crushing the new crossbow bolt feature, he asked me what the code looked like. I think he might have used verbiage like “what does it smell like?” but I can’t be certain. After pondering for a moment, thinking about “ice arrows” and “arcane bolts,” the code spoke to me. We had already outlined an interface for Projectile, which could encompass a whole range of new weaponry for the would-be wumpus hunter. I proceeded to extract out the new Projectile interface, and all the tests were still a beautiful shimmering green. He nodded satisfactorily, stood, said it was fun, and thanked me for pairing before leaving the workspace. It was a long while before I escaped my rumination and casually added in several new projectiles.

Shortly thereafter, my dad walked over and asked me how I enjoyed pairing with Ward Cunningham, the creator of the wiki. Suddenly, everything made sense. I had been coding with a legend, and legends don’t frolic with principles—they live and breathe them. Within about a year, my dad codified many of these same principles in the first edition of Clean Code .

I tell this story to highlight the profound impact that can be made when the disciplines, strategies, and principles within this book are taken to heart.

Over the years, I have founded or worked at over a dozen early-stage startups. Oftentimes, I’d join a small team of developers who already had a product out the door serving a vast user base. More often than not, the driving principle was to go fast at all costs. The website/app is too slow? Throw more hardware at it. Product development is going slow? Hire more developers and product managers to speed things up. Move fast and break things.

Gradually, however, as the industry matured, teams started to focus more and more on having a robust test base, continuous deployment, code reviews, and, critically, clean code. In almost every case, the teams that followed the disciplines and principles laid out in this book were the ones with the highest product velocity. At first, I served as a steady reminder for everyone to write tests, use clear naming, and clean up or refactor the code. These days, it is often a given that the team will already be practicing these principles. Why? Because they work. Much of the startup world has already adopted these lessons because it is a winning strategy. The goal is still to go as fast as possible, but as my dad is fond of saying, “The only way to go fast is to go well.”

The world of software development is changing fast. Advanced AI tools like Claude, Cursor, GPT-o, and Grok have made it easier than ever to produce working code. Developers are already using them to kick off projects, debug tricky errors, or even whip up fully tested versions of Hunt the Wumpus . This trend isn’t slowing down—it’s accelerating.

It is for this reason that Clean Code principles are more crucial now than ever. AI can churn out code like a factory, but it’s often like raw dough—tasty maybe, but not a fully baked pie. Clean Code is the recipe that turns it into something polished, whether you’re refactoring by hand or tweaking AI prompts to guide the process. It’s about crafting software that doesn’t just work, but lasts.

Whether you are using AI to write code or using AI as a personal Babel Fish to understand someone else’s code, if the intent is not inherent in the code, it is likely to be lost. Picture this: Grok spits out some code, you clean it up with Cursor and Claude, and it runs fine—until you realize it’s a tangled mess. So you ask GPT-o to sort it out, only to end up with a knot of interdependencies. Without Clean Code as a compass, AI’s output can quickly become a maintenance nightmare. The craft of writing clear, readable code remains essential.

As AI keeps evolving, it might one day churn out better code on its own—but don’t bet on it yet. Developers who stick to Clean Code principles will be the ones delivering high-quality, maintainable software no matter how smart AI gets. Clean Code is the guide that ensures you or your team’s work isn’t just functional—it’s something to be proud of.
