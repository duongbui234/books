# The Missing Chapter — Chương còn thiếu

By Simon Brown

> Tác giả: Simon Brown

All of the advice you’ve read so far will certainly help you **design** better software, composed of classes and components with well-defined boundaries, clear responsibilities, and controlled dependencies. But it turns out that the devil is in the implementation details, and it’s really easy to fall at the last hurdle if you don’t give that some thought, too.

> Tất cả những lời khuyên bạn đã đọc từ đầu tới giờ chắc chắn sẽ giúp bạn thiết kế phần mềm tốt hơn, gồm những class và component có ranh giới (boundary) rõ ràng, trách nhiệm minh bạch và các phụ thuộc được kiểm soát. Nhưng hoá ra ma quỷ nằm ở chi tiết cài đặt, và bạn rất dễ ngã ở rào chắn cuối cùng nếu không dành chút suy nghĩ cho cả chuyện đó nữa.

Let’s imagine that we’re building an online book store, and one of the use cases we’ve been asked to implement is about customers being able to view the status of their orders. Although this is a Java example, the principles apply equally to other programming languages. Let’s put the **Clean Architecture** to one side for a moment and look at a number of approaches to design and code organization.

> Hãy tưởng tượng chúng ta đang xây một hiệu sách trực tuyến, và một trong những use case ta được yêu cầu cài đặt là cho phép khách hàng xem trạng thái đơn hàng của họ. Dù đây là ví dụ bằng Java, các nguyên tắc vẫn áp dụng y hệt cho những ngôn ngữ lập trình khác. Hãy tạm gác Clean Architecture sang một bên và nhìn vào một loạt cách tiếp cận khác nhau đối với việc thiết kế và tổ chức mã nguồn.

## Package by Layer — Package by Layer

The first, and perhaps simplest, design approach is the traditional horizontal layered **architecture**, where we separate our code based on what it does from a technical perspective. This is often called “**package by layer**.” Figure 34.1 shows what this might look like as a UML class diagram.

> Cách tiếp cận thiết kế đầu tiên, và có lẽ cũng đơn giản nhất, là kiến trúc phân tầng theo chiều ngang truyền thống, trong đó ta tách mã nguồn dựa trên việc nó làm gì xét từ góc độ kỹ thuật. Cách này thường được gọi là "package by layer" (đóng gói theo tầng). Figure 34.1 cho thấy nó trông như thế nào dưới dạng một UML class diagram.

In this typical layered architecture, we have one layer for the web code, one layer for our “business logic,” and one layer for persistence. In other words, code is sliced horizontally into layers, which are used as a way to group similar types of things. In a “strict layered architecture,” layers should depend only on the next adjacent lower layer. In Java, layers are typically implemented as packages. ## Package by Feature — Package by Feature

Another option for organizing your code is to adopt a “package **by feature**” style. This is a vertical slicing, based on related features, domain concepts, or aggregate roots (to use domain-driven design terminology). In the typical implementations that I’ve seen, all of the types are placed into a single Java package, which is named to reflect the concept that is being grouped.

> Một lựa chọn khác để tổ chức mã nguồn là áp dụng phong cách "package by feature" (đóng gói theo tính năng). Đây là kiểu cắt dọc, dựa trên các tính năng liên quan, các khái niệm miền, hoặc các aggregate root (dùng thuật ngữ của domain-driven design). Trong những cài đặt điển hình mà tôi từng thấy, tất cả các kiểu đều được đặt vào một package Java duy nhất, được đặt tên phản ánh khái niệm đang được gom nhóm.

With this approach, as shown in Figure 34.2, we have the same interfaces and classes as before, but they are all placed into a single Java package rather than being split among three packages. This is a very simple refactoring from the “package by layer” style, but the top-**level** organization of the code now screams something about the business domain. We can now see that this code base has something to do with orders rather than the web, services, and repositories. Another benefit is that it’s potentially easier to find all of the code that you need to modify in the event that the “view orders” **use case** changes. It’s all sitting in a single Java package rather than being spread out. 3

> Với cách tiếp cận này, như minh hoạ ở Figure 34.2, ta vẫn có đúng những interface và class như trước, nhưng tất cả đều nằm trong một package Java duy nhất thay vì bị chia ra ba package. Đây là một refactoring rất đơn giản so với phong cách "package by layer", nhưng giờ đây cách tổ chức ở tầng cao nhất của mã nguồn đã gào lên điều gì đó về miền nghiệp vụ. Bây giờ ta thấy được rằng code base này có liên quan tới orders, chứ không phải tới web, services và repositories. ## Ports and Adapters — Ports and Adapters

As Uncle Bob has said, approaches such as “**ports and adapters**,” the “hexagonal architecture,” “boundaries, controllers, entities,” and so on aim to create architectures where business/domain-focused code is independent and separate from the technical implementation details such as frameworks and databases. To summarize, you often see such code bases being composed of an “inside” (domain) and an “outside” (infrastructure), as suggested in Figure 34.3.

> Như Uncle Bob đã nói, những cách tiếp cận kiểu "ports and adapters", "hexagonal architecture", "boundaries, controllers, entities", v.v. đều nhắm tới việc tạo ra các kiến trúc trong đó mã tập trung vào nghiệp vụ/miền là độc lập và tách biệt khỏi các chi tiết cài đặt kỹ thuật như framework và database. Tóm lại, bạn sẽ thường thấy những code base như vậy được cấu thành từ một phần "bên trong" (miền) và một phần "bên ngoài" (hạ tầng), như gợi ý ở Figure 34.3.

![](images/ch40-fig34-3.png)

## Package by Component — Package by Component

Although I agree wholeheartedly with the discussions about SOLID, REP, CCP, and CRP and most of the advice in this book, I come to a slightly different conclusion about how to organize code. So I’m going to present another option here, which I call “**package by component**.” To give you some background, I’ve spent most of my career building enterprise software, primarily in Java, across a number of different business domains. Those software systems have varied immensely, too. A large number have been web- based, but others have been client–server 4 , distributed, message-based, or something else. Although the technologies differed, the common theme was that the architecture for most of these software systems was based on a traditional layered architecture.

> Dù tôi hoàn toàn đồng tình với những thảo luận về SOLID, REP, CCP, CRP cùng phần lớn lời khuyên trong cuốn sách này, tôi lại đi tới một kết luận hơi khác về cách tổ chức mã nguồn. Vì vậy tôi sẽ trình bày ở đây thêm một lựa chọn nữa, mà tôi gọi là "package by component" (đóng gói theo component). Kể thêm chút bối cảnh: tôi đã dành phần lớn sự nghiệp để xây dựng phần mềm doanh nghiệp, chủ yếu bằng Java, trải khắp nhiều miền nghiệp vụ khác nhau. Những hệ thống phần mềm ấy cũng khác nhau vô cùng. Rất nhiều trong số đó dựa trên nền web, nhưng số khác lại là client–server 4 , phân tán, dựa trên thông điệp, hoặc một kiểu nào đó khác. Dù công nghệ khác nhau, điểm chung là kiến trúc của hầu hết những hệ thống phần mềm này đều dựa trên kiến trúc phân tầng truyền thống.

I’ve already mentioned a couple of reasons why layered architectures should be considered bad, but that’s not the whole story. The purpose of a layered architecture is to separate code that has the same sort of function. Web stuff is separated from business logic, which is in turn separated from data access. As we saw from the UML class diagram, from an implementation perspective, a layer typically equates to a Java package. From a code accessibility perspective, for the OrdersController to be able to have a dependency on the OrdersService interface, the OrdersService interface needs to be marked as public , because they are in different packages. Likewise, the OrdersRepository interface needs to be marked as public so that it can be seen outside of the repository package, by the OrdersServiceImpl class.

> Tôi đã nhắc tới vài lý do vì sao nên coi kiến trúc phân tầng là dở, nhưng đó chưa phải toàn bộ câu chuyện. Mục đích của kiến trúc phân tầng là gom riêng những đoạn mã có cùng loại chức năng vào một chỗ. Phần web được tách khỏi business logic, rồi business logic lại được tách khỏi phần truy cập dữ liệu. Như ta đã thấy từ UML class diagram, xét từ góc độ cài đặt, một tầng thường tương đương với một package Java. Xét từ góc độ khả năng truy cập mã, để OrdersController có thể phụ thuộc vào interface OrdersService , interface OrdersService phải được đánh dấu là public , bởi chúng nằm ở hai package khác nhau. Tương tự, interface OrdersRepository cũng phải được đánh dấu public để class OrdersServiceImpl có thể nhìn thấy nó từ bên ngoài package repository.

In a strict layered architecture, the dependency arrows should always point downward, with layers depending only on the next adjacent lower layer. This comes back to creating a nice, clean, acyclic dependency graph, which is achieved by introducing some rules about how elements in a code base should depend on each other. The big problem here is that we can cheat by introducing some undesirable dependencies, yet still create a nice, acyclic dependency graph.

> Trong một kiến trúc phân tầng nghiêm ngặt, các mũi tên phụ thuộc phải luôn chỉ xuống dưới, mỗi tầng chỉ phụ thuộc vào tầng liền kề bên dưới. Điều này quay lại chuyện tạo ra một đồ thị phụ thuộc đẹp, sạch, phi chu trình, đạt được bằng cách đặt ra vài quy tắc về việc các thành phần trong code base được phép phụ thuộc vào nhau như thế nào. Vấn đề lớn ở đây là ta vẫn có thể gian lận bằng cách đưa vào những phụ thuộc không mong muốn, mà đồ thị phụ thuộc thu được vẫn đẹp và vẫn phi chu trình.

Suppose that you hire someone new who joins your team, and you give the newcomer another orders -related use case to implement. Since the person is new, he wants to make a big impression and get this use case implemented as quickly as possible. After sitting down with a cup of coffee for a few minutes, the newcomer discovers an existing OrdersController class, so he decides that’s where the code for the new orders -related web page should go. But it needs some orders data from the database. The newcomer has an epiphany: “Oh, there’s an OrdersRepository interface already built, too. I can simply dependency-inject the implementation into my controller. Perfect!” After a few more minutes of hacking, the web page is working. But the resulting UML diagram looks like Figure 34.5.

> Giả sử bạn tuyển một người mới vào nhóm, và giao cho người mới ấy một use case khác liên quan tới orders để cài đặt. Vì là người mới, anh ta muốn tạo ấn tượng mạnh và hoàn thành use case này càng nhanh càng tốt. Sau vài phút ngồi nhâm nhi cà phê, người mới phát hiện ra đã có sẵn một class OrdersController , thế là anh ta quyết định đó chính là chỗ để đặt mã cho trang web mới liên quan tới orders. The dependency arrows still point downward, but the OrdersController is now additionally bypassing the OrdersService for some use cases. This organization is often called a relaxed layered architecture , as layers are allowed to skip around their adjacent neighbor(s). In some situations, this is the intended outcome—if you’re trying to follow the CQRS 5 pattern, for example. In many other cases, bypassing the business logic layer is undesirable, especially if that business logic is responsible for ensuring authorized access to individual records, for example.

> Các mũi tên phụ thuộc vẫn chỉ xuống dưới, nhưng giờ OrdersController còn đi vòng qua OrdersService ở một số use case. Cách tổ chức này thường được gọi là kiến trúc phân tầng nới lỏng (relaxed layered architecture), vì các tầng được phép nhảy cóc qua tầng kề bên. Trong một số tình huống, đó lại đúng là kết quả mong muốn — chẳng hạn nếu bạn đang cố theo mẫu CQRS 5 . This brings us to the “package by **component**” option. It’s a hybrid approach to everything we’ve seen so far, with the goal of bundling all of the responsibilities related to a single coarse-grained component into a single Java package. It’s about taking a service-centric view of a software system, which is something we’re seeing with **micro-service** architectures as well. In the same way that ports and adapters treat the web as just another delivery mechanism, “package by component” keeps the user interface separate from these coarse- grained components. A key benefit of the “package by component” approach is that if you’re writing code that needs to do something with orders , there’s just one place to go—the OrdersComponent . Inside the component, the separation of concerns is still maintained, so the business logic is separate from data persistence, but that’s a component implementation **detail** that consumers don’t need to know about. This is akin to what you might end up with if you adopted a micro-services or Service-Oriented Architecture—a separate OrdersService that encapsulates everything related to handling orders. The key difference is the **decoupling mode**. You can think of well-defined components in a monolithic application as being a stepping stone to a micro- services architecture.

> Một lợi ích then chốt của cách tiếp cận "package by component" là nếu bạn đang viết mã cần làm gì đó với orders , thì chỉ có đúng một chỗ để tìm tới — OrdersComponent . Bên trong component, việc tách bạch các mối quan tâm vẫn được duy trì, nên business logic vẫn tách khỏi phần lưu trữ dữ liệu, nhưng đó là chi tiết cài đặt bên trong component mà bên sử dụng không cần biết. Điều này gần giống với thứ bạn sẽ có nếu áp dụng micro-services hay Service-Oriented Architecture — một OrdersService riêng biệt đóng gói mọi thứ liên quan tới việc xử lý orders. Khác biệt mấu chốt nằm ở chế độ tách rời (decoupling mode). Bạn có thể coi những component được định nghĩa rõ ràng trong một ứng dụng nguyên khối như bậc đá lót đường tiến tới kiến trúc micro-service.

## The Devil Is in the Implementation Details — Ma quỷ nằm ở chi tiết cài đặt

On the face of it, the four approaches do all look like different ways to organize code and, therefore, could be considered different architectural styles. This perception starts to unravel very quickly if you get the implementation details wrong, though.

> Thoạt nhìn, cả bốn cách tiếp cận đều có vẻ chỉ là những cách khác nhau để tổ chức mã nguồn, và vì thế có thể xem là những phong cách kiến trúc khác nhau. Nhưng cảm nhận ấy sẽ nhanh chóng sụp đổ nếu bạn làm sai các chi tiết cài đặt.

Something I see on a regular basis is an overly liberal use of the public access modifier in languages such as Java. It’s almost as if we, as developers, instinctively use the public keyword without thinking. It’s in our muscle memory. If you don’t believe me, take a look at the code samples for books, tutorials, and open source frameworks on GitHub. This tendency is apparent, regardless of which architectural style a code base is aiming to adopt— horizontal layers, vertical layers, ports and adapters, or something else.

> Thứ tôi thấy đều đặn là việc lạm dụng quá mức bổ từ truy cập public trong những ngôn ngữ như Java. Cứ như thể chúng ta, những lập trình viên, theo bản năng gõ từ khoá public mà chẳng cần nghĩ. Nó nằm trong trí nhớ cơ bắp của ta rồi. Nếu bạn không tin, hãy thử nhìn vào mã ví dụ của các cuốn sách, các bài hướng dẫn và các framework mã nguồn mở trên GitHub. Xu hướng này lộ rõ, bất kể code base ấy đang nhắm tới phong cách kiến trúc nào — phân tầng ngang, phân tầng dọc, ports and adapters, hay thứ gì khác.

Marking all of your types as public means you’re not taking advantage of the facilities that your programming language provides with regard to **encapsulation**. In some cases, there’s literally nothing preventing somebody from writing some code to instantiate a concrete implementation class directly, violating the intended architecture style.

> Đánh dấu mọi kiểu của bạn là public nghĩa là bạn đang không tận dụng những phương tiện mà ngôn ngữ lập trình cung cấp cho việc đóng gói (encapsulation). Trong một số trường hợp, đúng nghĩa đen là chẳng có gì ngăn được ai đó viết đoạn mã khởi tạo trực tiếp một class cài đặt cụ thể, vi phạm phong cách kiến trúc đã định.

## Organization versus Encapsulation — Tổ chức so với đóng gói

Looking at this issue another way, if you make all types in your Java application public , the packages are simply an organization mechanism (a grouping, like folders), rather than being used for encapsulation. Since public types can be used from anywhere in a code base, you can effectively ignore the packages because they provide very little real value. The net result is that if you ignore the packages (because they don’t provide any means of encapsulation and hiding), it doesn’t really matter which architectural style you’re aspiring to create. If we look back at the example UML diagrams, the Java packages become an irrelevant detail if all of the types are marked as public . In essence, all four architectural approaches presented earlier in this chapter are exactly the same when we overuse this designation (Figure 34.7).

> Nhìn vấn đề theo một góc khác: nếu bạn đánh dấu mọi kiểu trong ứng dụng Java của mình là public , thì package chỉ còn là cơ chế tổ chức (một cách gom nhóm, như thư mục), chứ không còn được dùng để đóng gói nữa. Vì kiểu public có thể được dùng từ bất cứ đâu trong code base, bạn hoàn toàn có thể phớt lờ các package bởi chúng mang lại rất ít giá trị thực. Kết quả cuối cùng là nếu bạn phớt lờ các package (vì chúng chẳng cung cấp phương tiện đóng gói và che giấu nào), thì việc bạn khát khao tạo ra phong cách kiến trúc nào cũng chẳng còn mấy ý nghĩa. Nhìn lại các sơ đồ UML ví dụ, các package Java trở thành một chi tiết vô nghĩa nếu tất cả các kiểu đều được đánh dấu public . Về bản chất, cả bốn cách tiếp cận kiến trúc trình bày ở đầu chương này là y hệt nhau khi ta lạm dụng bổ từ ấy (Figure 34.7).

This is a neat trick, and of course nobody would ever make all of their Java types public . Except when they do. And I’ve seen it.

Just to be absolutely clear, what I’ve described here relates to a monolithic application, where all of the code resides in a single source code tree. If you are building such an application (and many people are), I would certainly encourage you to lean on the compiler to enforce your architectural principles, rather than relying on self-discipline and post-compilation tooling.

> Nói cho thật rõ ràng: những gì tôi mô tả ở đây liên quan tới một ứng dụng nguyên khối, nơi toàn bộ mã nguồn nằm trong một cây mã nguồn duy nhất. Nếu bạn đang xây một ứng dụng như vậy (và rất nhiều người đang làm thế), tôi chắc chắn khuyến khích bạn dựa vào trình biên dịch để thực thi các nguyên tắc kiến trúc của mình, thay vì trông cậy vào tính tự giác và các công cụ chạy sau biên dịch.

## Other Decoupling Modes — Các chế độ tách rời khác

In addition to the programming language you’re using, there are often other ways that you can decouple your source code dependencies. With Java, you have module frameworks like OSGi and the new Java 9 module system. With module systems, when used properly, you can make a distinction between types that are public and types that are published . For example, you could create an Orders module where all of the types are marked as public , but publish only a small subset of those types for external consumption. It’s been a long time coming, but I’m enthusiastic that the Java 9 module system will give us another tool to build better software, and spark people’s interest in design thinking once again.

> Ngoài chính ngôn ngữ lập trình bạn dùng, thường vẫn còn những cách khác để tách rời các phụ thuộc mã nguồn. Với Java, bạn có các framework module như OSGi và hệ thống module mới của Java 9. Với hệ thống module, khi dùng đúng cách, bạn có thể phân biệt giữa các kiểu là public và các kiểu được published . Chẳng hạn, bạn có thể tạo một module Orders trong đó mọi kiểu đều được đánh dấu public , nhưng chỉ publish một tập con nhỏ trong số đó cho bên ngoài dùng. Phải chờ khá lâu, nhưng tôi rất hào hứng khi nghĩ tới việc hệ thống module của Java 9 sẽ cho chúng ta thêm một công cụ nữa để xây phần mềm tốt hơn, và một lần nữa khơi lại hứng thú của mọi người với tư duy thiết kế.

From an implementation perspective, you can do this by configuring separate modules or projects in your build tool (e.g., Maven, Gradle, MSBuild). Ideally you would repeat this pattern, having a separate source code tree for each and every component in your application.

> Hai cây mã nguồn sau có phụ thuộc lúc biên dịch vào phần mã nghiệp vụ và miền, còn bản thân phần mã đó chẳng biết gì về mã web hay mã lưu trữ dữ liệu. This is very much an idealistic solution, though, because there are real-world performance, complexity, and maintenance issues associated with breaking up your source code in this way.

> Tuy nhiên đây là một giải pháp mang tính lý tưởng hoá, bởi việc xé nhỏ mã nguồn theo kiểu này kéo theo những vấn đề rất thật về hiệu năng, độ phức tạp và bảo trì.

## Conclusion: The Missing Advice — Kết luận: Lời khuyên còn thiếu

The whole point of this chapter is to highlight that your best design intentions can be destroyed in a flash if you don’t consider the intricacies of the implementation strategy. Think about how to map your desired design on to code structures, how to organize that code, and which **decoupling** modes to apply during runtime and compile-time. Leave options open where applicable, but be pragmatic, and take into consideration the size of your team, their skill level, and the complexity of the solution in conjunction with your time and budgetary constraints. Also think about using your compiler to help you enforce your chosen architectural style, and watch out for coupling in other areas, such as data models. The devil is in the implementation details.

> Toàn bộ ý của chương này là để nhấn mạnh rằng những ý đồ thiết kế tốt đẹp nhất của bạn có thể tan tành trong chớp mắt nếu bạn không cân nhắc tới sự tinh vi của chiến lược cài đặt. Hãy nghĩ xem làm sao ánh xạ thiết kế mong muốn của bạn xuống các cấu trúc mã, tổ chức mã đó ra sao, và áp dụng chế độ tách rời nào lúc chạy và lúc biên dịch. Hãy để ngỏ các lựa chọn ở những chỗ phù hợp, nhưng hãy thực dụng, và cân nhắc quy mô của nhóm, trình độ của họ, độ phức tạp của giải pháp, đặt cạnh những ràng buộc về thời gian và ngân sách. Cũng hãy nghĩ tới việc dùng trình biên dịch để giúp bạn thực thi phong cách kiến trúc đã chọn, và để mắt tới sự kết dính ở những vùng khác nữa, chẳng hạn như mô hình dữ liệu. Ma quỷ nằm ở chi tiết cài đặt.
